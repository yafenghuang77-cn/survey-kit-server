## 3.2 认证方案（Sa-Token）

| 项 | 选型 |
|----|------|
| 框架 | **Sa-Token** |
| 形态 | 网关统一拦截 + 各服务注解鉴权 |
| 存储 | Redis（会话、踢人、多端登录） |
| 入口 | `survey-kit-auth` 只做业务账号与登录接口，token 签发/校验交给 Sa-Token |

### Token 认证规则（约定）

1. **默认全量鉴权**：所有接口默认需要登录（带 token），不搞「默认放行」。
2. **白名单用注解**：无需登录的接口用注解标记（如 Sa-Token 的 `@SaIgnore`，或统一自定义 `@Anonymous`），**禁止**用 yml/文件配置接口路径列表。
3. **登录后写浏览器**：token 生成/登录成功后，由后端写入浏览器 **Cookie**（HttpOnly，按需 Secure/SameSite）。
4. **默认自动带回**：后续调用接口由浏览器自动带上 Cookie 中的 token。
5. **同时支持显式携带**：前端也可在请求头携带 token（如 `Authorization: Bearer xxx` 或 Sa-Token 默认头），用于小程序 / App / 调试等无 Cookie 场景；头优先于 Cookie。
6. **多端可用**：Cookie 与 Header 两种方式并存，会话同一账号体系（Redis）。

### Token 读取顺序（建议）

```text
请求头 Authorization / satoken  →  Cookie  →  未登录
```

### 职责划分

```text
Gateway   → Sa-Token 全局过滤器：默认强制登录、注解放行、路由白名单（仅网关级横切）
auth 服务 → 登录/登出/改密等业务；登录成功写 Cookie + 返回 token
业务服务  → @SaCheckRole / @SaCheckPermission 细粒度鉴权；@SaIgnore 标注免登录接口
```

**不造轮子的边界：** 不手写 JWT 签发/解析/过滤器；登录页与账号体系仍归 auth。免登录接口只靠注解，不维护路径配置文件。

## 3.3 统一响应体与全局异常（COLA 全量）

| 项 | 选型 |
|----|------|
| 方案 | **COLA v5 全量组件**（`com.alibaba.cola`） |
| 茁围 | 架构分层 + **全部** `cola-components` 统一安装 |
| 对外字段 | `success` / `errCode` / `errMessage` / `data` / `traceId` |
| 不用 | Graceful Response（避免双套出口） |

### COLA 组件清单（全部安装）

| 组件 | 功能 | 依赖 |
|------|------|------|
| `cola-component-dto` | DTO 格式（含分页） | 无 |
| `cola-component-exception` | 异常格式（`BizException` / `SysException`） | 无 |
| `cola-component-statemachine` | 状态机 | 无 |
| `cola-component-domain-starter` | Spring 托管的领域实体 | 无 |
| `cola-component-catchlog-starter` | 异常处理和日志 | exception、dto |
| `cola-component-extension-starter` | 扩展点 | 无 |
| `cola-component-test-container` | 测试容器 | 无 |
| `cola-component-unittest` | 单元测试支持（v5） | — |

> 坐标前缀：`com.alibaba.cola:cola-component-*`；版本与 COLA **5.x** 对齐。

### COLA 架构（一并采用）

| 部分 | 用途 |
|------|------|
| **COLA 分层** | adapter / app / domain / infrastructure / start |
| `cola-archetype-web` | Web 应用骨架（adapter + 服务一体） |
| `cola-archetype-service` | 纯后端服务骨架 |
| `cola-archetype-light` | 基于 package 的轻量分层（v5） |

脚手架可用 archetype 生成，或手按 COLA 包结构落地到 `survey-kit-*` 模块。

### 响应体约定

| 字段 | 类型 | 成功 | 失败 |
|------|------|------|------|
| `success` | boolean | `true` | `false` |
| `errCode` | string/null | **`null`** | 业务错误码 |
| `errMessage` | string/null | **`null`** | 错误信息 |
| `data` | any/null | 业务数据（无数据则 `null`） | 通常为 `null` |
| `traceId` | string | **始终返回**，便于排查 | **始终返回** |

### JSON 示例

**成功（有数据）：**

```json
{
  "success": true,
  "errCode": null,
  "errMessage": null,
  "data": {
    "id": 1,
    "name": "张三"
  },
  "traceId": "0a1b2c3d4e5f6789"
}
```

**成功（无数据）：**

```json
{
  "success": true,
  "errCode": null,
  "errMessage": null,
  "data": null,
  "traceId": "0a1b2c3d4e5f6789"
}
```

**业务失败：**

```json
{
  "success": false,
  "errCode": "3001",
  "errMessage": "操作失败原因说明",
  "data": null,
  "traceId": "0a1b2c3d4e5f6789"
}
```

**参数校验失败：**

```json
{
  "success": false,
  "errCode": "1001",
  "errMessage": "参数校验失败的具体说明",
  "data": null,
  "traceId": "0a1b2c3d4e5f6789"
}
```

**未登录 / 无权限（与 Sa-Token 对齐）：**

```json
{
  "success": false,
  "errCode": "2001",
  "errMessage": "未登录",
  "data": null,
  "traceId": "0a1b2c3d4e5f6789"
}
```

### 实现要点

1. **响应体**：扩展 COLA `Response` / `SingleResponse` / `MultiResponse`，或统一自定义 `ApiResult`，必须包含 `traceId`；**成功时 `errCode` 为 null**（不要用 COLA 默认的 `"OK"`）。
2. **全局异常**：用 `cola-component-exception`（`BizException` / `SysException`）+ `cola-component-catchlog-starter`，再按需 `@RestControllerAdvice` 补出口，统一转上述 JSON。
3. **traceId**：请求入口生成或透传（MDC + Filter/Interceptor），日志与响应同一 `traceId`。
4. **data 字段始终存在**：无数据显式 `null`，不要省略字段。
5. **HTTP 状态**：业务失败仍可用 200（以 `success` 判断）；未登录/无权限是否用 401/403 与 Sa-Token 配置对齐后写死，前端只认一种约定。
6. **扩展点 / 状态机 / 领域实体**：按需在业务模块中启用 `extension-starter`、`statemachine`、`domain-starter`。
7. **测试**：`test-container` + `unittest` 用于模块单测/集成测试。

### 错误码分段（建议）

| 段 | 含义 |
|----|------|
| `1xxx` | 参数 / 校验 |
| `2xxx` | 认证 / 授权（Sa-Token） |
| `3xxx` | 业务 |
| `5xxx` | 系统 |

## 3.4 持久层与分页（MyBatis-Plus）

| 项 | 选型 |
|----|------|
| ORM | **MyBatis-Plus**（默认） |
| 连接池 | Druid（SCA BOM 已管版本） |
| 驱动 | MySQL Connector/J |
| 分页 | **MyBatis-Plus 自带能力**（`Page` / `IPage` + `PaginationInnerInterceptor`）✅ 已定 |

### 分页方案

**已定：直接使用 MyBatis-Plus 分页能力，不引入 PageHelper 等第三方分页插件。**

| 方案 | 说明 | 结论 |
|------|------|------|
| **A. MP 内置分页** | `IPage` / `Page<T>` + `PaginationInnerInterceptor`，物理分页 | ✅ **已定** |
| B. PageHelper | 第三方插件，ThreadLocal 风格 | 不采用 |
| C. 手写 LIMIT | 样板多 | 仅特殊 SQL |
| D. 瀑布流 / 游标 | 大列表导出等 | 按需单独设计 |

**推荐组合（A + COLA 出参）：**

```text
请求:  page / pageSize / sort（可选）     ← 对外查询参数
查询:  MP Page + Service/Mapper
响应:  data = { records, total, page, pageSize, size... }
外层:  success / errCode / errMessage / data / traceId
```

**分页出参结构（在 `data` 内）：**

```json
{
  "success": true,
  "errCode": null,
  "errMessage": null,
  "data": {
    "records": [],
    "total": 0,
    "page": 1,
    "pageSize": 20
  },
  "traceId": "..."
}
```

实现要点：

1. 仅在 **配置类** 注册 `PaginationInnerInterceptor`（可配最大页大小）
2. 对外分页对象与 MP `Page` 解耦，避免持久层类型漏出 API
3. COLA `dto` 里的分页规范可对齐命名（`page` / `pageSize` / `records` / `total`）
4. 复杂报表可用自定义 SQL + 手写分页，仍保持同一响应壳

## 5. 服务 / 模块划分

> 架构：**微服务 + Gateway**。

```text
survey-kit-server
├── survey-kit-gateway            # 统一入口：路由、鉴权过滤、限流入口
├── survey-kit-common             # 公共：统一响应、异常、工具、traceId
├── survey-kit-auth               # 认证登录（可与用户中心合并部署，见下）
├── survey-kit-user-center        # 用户中心：用户、角色、权限管理与查询
└── survey-kit-survey             # 问卷服务：问卷设计、推送、作答/问答
```

### 子服务职责

| 服务 | 职责 |
|------|------|
| **survey-kit-user-center** | 用户中心（用户 / 角色 / 权限相关管理与查询） |
| **survey-kit-survey** | 问卷服务（设计、推送、作答/问答） |
| **survey-kit-auth** | 认证（Sa-Token）；可与 user-center 合并部署或独立 |
| **survey-kit-gateway** | 网关（路由、默认鉴权、路径前缀、traceId） |
| **survey-kit-common** | 公共（COLA 响应壳、错误码、工具） |

**边界：** user-center 管「人和权限」，survey 管「问卷业务」。服务间如何调用在设计阶段定，规划不展开接口。

### 服务端口与环境前缀（约定）

| survey | 9012 | 经 gateway 路由 |
| auth | 9013（若独立） | 经 gateway 路由 |

## 9. 风险与注意事项

1. **版本矩阵错乱**是最大坑：Boot / Cloud / SCA 三者必须严格对齐，禁止混用 2023.x 与 2025.x。
2. **COLA v5.0.0 标称支持 JDK 17 + Boot 3.x**：Boot 4 需在落地前用真实工程验证 catchlog 等 starter 是否兼容；不兼容则只引 dto/exception 等无 Spring 绑定组件。
3. **Nacos 2.x/3.x 的 gRPC 长连接**：默认端口 9848/9849，容器网络需放行。
3. **Sentinel 规则默认在内存**：重启丢失，生产需推到 Nacos 持久化。
4. **Seata AT 模式有全局锁**：热点行更新会掉吞吐，该用 TCC / 最终一致性时别硬上 AT。
5. **Boot 4 注解与配置项有变化**：从 Boot 3 迁移时注意废弃项。
